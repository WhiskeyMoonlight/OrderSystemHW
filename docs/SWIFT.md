# Чекер для Swift-домашек

Инструкция для автора задания: как подготовить Swift-ДЗ, собрать бинарь `checker` и положить его в репозиторий задания.

## 1. Главное: кто что делает

Тестов в задании **две копии**, и роли у них разные:

| | Локальные тесты студента | Эталонные тесты в бинаре |
|---|---|---|
| Где лежат | `Tests/` в репозитории задания | внутри `.github/checker`, в сжатом виде |
| Откуда берутся | копия из шаблона `templates/swift-homework` | из `payload/swift/tests/` при сборке бинаря |
| Кто может менять | студент — как угодно | только мы, пересобрав бинарь |
| Зачем | студент гоняет их у себя: `swift test` | **только они решают, засчитано ли задание** |

Порядок работы:

```
МЫ, при подготовке ДЗ (один раз на задание)
  payload/swift/tests/  ──./build.sh swift──►  dist/checker-swift-linux-amd64
                                                       │
                                                       ▼
  репозиторий задания:  .github/checker   ← кладём бинарь сюда
                        Sources/          ← заглушки, их реализует студент
                        Tests/            ← локальные тесты для студента
                        config.yml        ← студент впишет свой токен LMS

СТУДЕНТ
  пишет код в Sources/, гоняет и как угодно меняет свои Tests/, делает push

CI (GitHub Actions) на каждый push
  .github/checker → удаляет Tests/ студента → кладёт эталонные тесты
                  → swift test → все зелёные? → засчитывает задание в LMS
```

Что из этого следует:
- **Студент ничего не собирает.** Бинарь собираем мы, при формировании ДЗ, и коммитим его в репозиторий задания.
- **Локальные тесты ни на что не влияют.** Если студент их ослабит или удалит, у него локально будет зелёно, а в CI — нет: там гоняются эталонные.
- **Засчитать задание может только бинарь.** Он проверяет именно то, что вшито в него при сборке.
- **Поменяли эталонные тесты — пересоберите бинарь** и закоммитьте новый `.github/checker` в репозиторий задания.

Сам чекер написан на Go (так его проще собрать под Linux и macOS одной командой). Код на Go трогать не нужно.

## 2. Что установить

| Что | Зачем | Как |
|---|---|---|
| Xcode 16+ (Swift 6) | писать и прогонять тесты | App Store |
| Go 1.21+ | собирать бинарь | `brew install go` |
| Docker (желательно) | проверить тесты под Linux, где работает CI | Docker Desktop или OrbStack |

Проверка: `swift --version` и `go version` должны что-то вывести.

Нужно это только нам, авторам задания. Студенту достаточно Xcode.

## 3. Где лежат тесты

```
course-checker/
├── payload/swift/
│   ├── tests/OrdersTests/       ← ЭТАЛОННЫЕ ТЕСТЫ: вшиваются в бинарь
│   ├── pinned/Package.swift     не трогать (см. раздел 12)
│   └── toolchain.json           не трогать, кроме minTests (см. раздел 9)
├── templates/swift-homework/    шаблон репозитория задания
│   ├── Sources/Orders/          заглушки для студента
│   └── Tests/OrdersTests/       ← ЛОКАЛЬНЫЕ ТЕСТЫ: копия для студента
├── build.sh                     сборка бинаря
└── docs/SWIFT.md                эта инструкция
```

**Эталонные тесты** — `payload/swift/tests/`. Всё, что там лежит, при проверке копируется как есть в папку `Tests/` репозитория студента, поверх его собственной. Тестовый таргет в `Package.swift` называется `OrdersTests` и смотрит в `Tests/OrdersTests`, поэтому файлы кладутся в `payload/swift/tests/OrdersTests/`.

**Локальные тесты** — `templates/swift-homework/Tests/OrdersTests/`. Это то, что студент получит в репозитории и сможет запускать. Обычно это та же копия, что и эталон: студент видит, что от него ждут, и локальный прогон совпадает с CI. Но можно дать и часть тестов. На проверку эта папка не влияет никак.

Сейчас в обеих папках лежат одинаковые файлы-примеры:
- `TestFixtures.swift` — общие хелперы: `product()`, `coffee()`, `orderOf(...)`, `assertInvalidArgument`, `assertInvalidState`;
- `ProductTests.swift` — 11 тестов для `Product`, перенесённые из Kotlin-версии.

Их можно менять, дополнять или заменить целиком. Если меняете эталон и хотите, чтобы студенты видели то же самое, скопируйте его и в шаблон:

```bash
cp payload/swift/tests/OrdersTests/*.swift templates/swift-homework/Tests/OrdersTests/
```

## 4. API, против которого пишутся тесты

Тесты — отдельный модуль, поэтому в каждом файле нужно:

```swift
import XCTest
@testable import Orders
```

API задания — заглушки в `templates/swift-homework/Sources/Orders/*.swift`. Это перенос Kotlin-версии (`Product`, `Order`, `OrderSystem`, скидки и т.д.): тела функций — `fatalError("TODO")`, их пишет студент. Kotlin-исключения заменены на ошибки Swift:

| Kotlin | Swift |
|---|---|
| `IllegalArgumentException` | `throw OrderError.invalidArgument("...")` |
| `IllegalStateException` | `throw OrderError.invalidState("...")` |
| `Long` (копейки) | `Int` (64-битный на всех платформах CI) |

API можно менять как угодно, но заглушки и тесты должны друг другу соответствовать. Если меняете сигнатуры в шаблоне, обновите их **до** выдачи задания студентам.

## 5. Правила для эталонных тестов (иначе всё сломается в CI)

CI работает на **Linux** (`ubuntu-latest` + Docker-образ `swift:6.1`), а не на macOS. Всё, что есть только у Apple, там не соберётся. Тогда **у каждого студента** пайплайн упадёт с сообщением «проект не скомпилировался», хотя виноват будет не он.

**Можно:** `XCTest`, стандартная библиотека, базовый `Foundation` (строки, коллекции, `trimmingCharacters` и т.п.).

**Нельзя:**
- `UIKit`, `SwiftUI`, `Combine`, `CoreData`, `OSLog`/`os.log` — на Linux их нет;
- `XCTMetric`, `measure(metrics:)`, UI-тесты;
- `Decimal`/`NSDecimalNumber` для денег: на Linux другая реализация, с отличиями в округлении и выводе. Только целые копейки;
- тесты на `DateFormatter`/`Locale`, если результат зависит от локали машины;
- `@Test`/`#expect` (swift-testing): сейчас их результаты не попадают в отчёт. Такой тест не посчитается, и чекер упадёт на проверке `minTests`. Пишите на XCTest;
- зависимости в `Package.swift`;
- функции задания с именами методов `XCTestCase` (`add`, `measure`, `expectation`, `wait`…): вызов `add(2, 3)` в тесте не скомпилируется, потому что компилятор найдёт метод класса, а не функцию задания.

Хорошо бы, чтобы каждый тест был независимым и не зависел от порядка запуска: тесты гоняются параллельно.

## 6. Как прогнать эталонные тесты локально

Соберите шаблон с эталонными тестами во временной папке и запустите их:

```bash
rm -rf /tmp/hw && cp -R templates/swift-homework /tmp/hw
cp -R payload/swift/tests/. /tmp/hw/Tests/
cd /tmp/hw && swift test --parallel
```

На заглушках тесты упадут, это нормально. Чтобы убедиться, что тесты корректны, напишите в `/tmp/hw/Sources/Orders` эталонное решение: все тесты должны пройти. Эталонное решение в репозиторий чекера и в шаблон не кладите.

## 7. Проверка под Linux (очень желательно)

Из `/tmp/hw` с эталонным решением:

```bash
docker run --rm -v "$PWD":/w -w /w swift:6.1 swift test --parallel
```

Если тут всё зелёное, в CI тоже будет зелёное. Если не собирается, значит, где-то использован API из раздела 5.

## 8. Токены

Для сборки и работы чекера нужны три значения:

| Значение | Что это | Где взять | Когда нужно |
|---|---|---|---|
| `LMS_COMPANY_TOKEN` | токен компании в LMS, которым чекер подписывает запрос | у владельца курса | при сборке бинаря (нам) |
| `CALLBACK_TASK_ID` | ID конкретного задания в LMS | у владельца курса / в LMS | при сборке бинаря (нам); **у каждого задания свой**, поэтому и бинарь на каждое задание собирается свой |
| `user_token` | личный токен студента | студент берёт в личном кабинете LMS | при проверке в CI; студент вписывает его в `config.yml` |

**Как они попадают в бинарь.** `build.sh` вшивает `LMS_COMPANY_TOKEN` и `CALLBACK_TASK_ID` в бинарь при сборке. Если их не задать, сборка сразу остановится с ошибкой «нужно задать LMS_COMPANY_TOKEN». В файлах они нигде не хранятся: передавайте их только через переменные окружения в команде сборки.

**Как читается `user_token`.** `config.yml` в корне репозитория студента:

```yaml
# Вставьте сюда свой токен из личного кабинета LMS.
user_token: PASTE_YOUR_TOKEN_HERE
```

Значение можно писать в кавычках или без, комментарий после него допускается. Если файла нет, поле пустое или в нём осталась заглушка `PASTE_YOUR_TOKEN_HERE`, чекер завершится с понятной ошибкой ещё до запуска тестов.

**Что уходит в LMS** (только если все эталонные тесты зелёные):

```
POST https://lms.metaclass.kts.studio/api/v2.chunk.check_callback_task
Authorization: Bearer <LMS_COMPANY_TOKEN>
Content-Type: application/json

{
  "created": "2026-09-21T12:00:00Z",
  "task_id": "<CALLBACK_TASK_ID>",
  "user_token": "<user_token студента>",
  "extra": { "student_repo": "owner/repo", "student_ref": "refs/heads/main" }
}
```

`student_repo` и `student_ref` берутся из переменных GitHub Actions (`GITHUB_REPOSITORY`, `GITHUB_REF`). При локальном запуске — из `git`, а если не получилось, пишется `local`. При ответе 5xx или сетевой ошибке чекер делает ещё две попытки с паузами 2 и 4 секунды. Ответ 4xx (неверный токен компании, неизвестный task_id, неверный токен студента) считается окончательным отказом.

**Режим `--dry-run`** делает всё, кроме отправки в LMS. Для локальной проверки подходят любые фиктивные токены (главное, чтобы они не начинались с `@`) и любой `user_token`, кроме заглушки.

> ⚠️ **Безопасность.** Тесты в бинаре сжаты, простым `grep` их не найти. А токены лежат в нём **открытым текстом**: `strings .github/checker` их покажет. Бинарь коммитится в репозиторий студента, значит `LMS_COMPANY_TOKEN` фактически виден любому студенту, который захочет его найти. Так устроен и Kotlin-чекер. Поэтому:
> - не пересылайте токен в чатах и не сохраняйте его в файлах репозитория чекера;
> - если в LMS можно выпустить токен с правами только на callback, используйте такой;
> - если токен утёк, попросите владельца курса его перевыпустить и пересоберите бинари всех заданий.

## 9. Сборка бинаря

Из корня репозитория чекера:

```bash
LMS_COMPANY_TOKEN=<токен> CALLBACK_TASK_ID=<id задания> ./build.sh swift
```

Скрипт по порядку:
1. проверяет, что токены заданы и что в `payload/swift/tests/` есть файлы;
2. проверяет, что `payload/swift/pinned/Package.swift` совпадает с `templates/swift-homework/Package.swift`;
3. упаковывает эталонные тесты в архив и прогоняет тесты самого чекера;
4. собирает бинарь под вашу машину и проверяет, что он читает свой `toolchain.json`;
5. собирает остальные платформы.

Результат:

```
dist/checker-swift-linux-amd64    ← этот кладём в репозиторий задания (для GitHub Actions)
dist/checker-swift-linux-arm64
dist/checker-swift-darwin-arm64   ← этим удобно проверять локально на Mac
dist/checker-swift-darwin-amd64
```

Локальные тесты из шаблона в бинарь не попадают: в него вшивается только `payload/swift/tests/`.

**`minTests` — обязательно настройте после написания эталонных тестов.** В `payload/swift/toolchain.json` есть поле `"minTests": 1`. Это минимальное число тестов, которые должны реально запуститься. Оно ловит два случая: студент как-то исключил тесты из сборки, или тест написан на swift-testing и не попал в отчёт. Как выставить:
1. соберите бинарь и прогоните его на эталонном решении (раздел 10, «Проверка перед выдачей»);
2. в строке `[checker] тестов: N, ...` возьмите число N;
3. впишите его в `minTests` и пересоберите.

## 10. Формирование ДЗ

1. Создайте репозиторий задания из шаблона: скопируйте содержимое `templates/swift-homework/` в новый репозиторий. Локальные тесты для студента уже лежат в `Tests/OrdersTests/`.
2. Соберите бинарь и сразу положите его в репозиторий задания:
   ```bash
   INSTALL_TO=/путь/к/репозиторию-задания \
   LMS_COMPANY_TOKEN=<токен> CALLBACK_TASK_ID=<id задания> ./build.sh swift
   ```
   Бинарь `checker-swift-linux-amd64` будет скопирован в `<репозиторий>/.github/checker`. Workflow `.github/workflows/check.yml` уже есть в шаблоне.
3. Проверьте задание (ниже).
4. Закоммитьте всё, включая `.github/checker`, и выдайте студентам.

Если позже поменяете эталонные тесты, `Package.swift` или ID задания — повторите шаг 2 и закоммитьте новый `.github/checker`. Студентам ничего пересобирать не нужно.

**Проверка перед выдачей** (на Mac, с эталонным решением в `/tmp/hw` из раздела 6):

```bash
cp dist/checker-swift-darwin-arm64 /tmp/hw/checker
cd /tmp/hw && sed -i '' 's/PASTE_YOUR_TOKEN_HERE/test/' config.yml
./checker --dry-run
```

Ожидаемый результат: `[checker] тестов: N, прошло: N, упало: 0, пропущено: 0` и код выхода 0. Под Linux то же самое: `docker run --rm -v /tmp/hw:/w -w /w swift:6.1 ./checker-linux --dry-run`, скопировав туда `dist/checker-swift-linux-amd64` (или `linux-arm64` на Mac с Apple Silicon).

Какие эталонные тесты вшиты в бинарь, по нему самому не видно (они сжаты). Посмотреть тулчейн и `minTests` можно так: `./checker -print-manifest`.

## 11. Сообщения чекера

| Сообщение | Причина | Что делать |
|---|---|---|
| `нужно задать LMS_COMPANY_TOKEN` (при сборке) | не передан токен | см. раздел 8 |
| `payload/swift/tests/ пуст` | нет эталонных тестов | положите `*.swift` в `payload/swift/tests/OrdersTests/` |
| `... отличается от templates/swift-homework/Package.swift` | правили один `Package.swift`, а не оба | сделайте их одинаковыми |
| `toolchain.json не прошёл проверку` | опечатка в `toolchain.json` | верните файл из git, поменяйте только `minTests` |
| `бинарь собран без LMS_COMPANY_TOKEN` | бинарь собран не через `build.sh` | соберите через `build.sh` |
| `в config.yml не заполнен user_token` | студент не вписал токен | студенту: вписать токен из личного кабинета |
| `в корне проекта нет файла config.yml` | студент удалил файл | вернуть из шаблона |
| `отчётов о тестах нет — скорее всего проект не скомпилировался` | не собрались код студента **или эталонные тесты** | если так у всех студентов, скорее всего в тестах API только для macOS (раздел 5) или тесты не совпадают с заглушками |
| `тестов: N, прошло: M, упало: K` + `есть упавшие...` | обычный красный прогон | студенту: чинить решение. Упавший `fatalError("TODO")` тоже считается упавшим тестом |
| `прогнано тестов: N, ожидалось не меньше M` | часть тестов не запустилась | проверьте, нет ли `@Test`; у студента — не правил ли он сборку |
| `LMS отклонила результат: статус 401/403` | неверный `LMS_COMPANY_TOKEN` | пересоберите с правильным токеном |
| `LMS отклонила результат: статус 400/404` | неверный `CALLBACK_TASK_ID` или `user_token` | проверьте ID задания; студенту — токен |
| `не удалось отправить результат за 3 попытки` | LMS недоступна | перезапустить job позже |

Частый вопрос студента: «локально всё зелёное, а в CI красное». Обычно это значит, что студент менял свои локальные тесты, а CI гоняет эталонные. Пусть вернёт `Tests/` из шаблона и прогонит ещё раз.

Почему тесты гоняются с `--parallel`: в этом режиме каждый тест выполняется в отдельном процессе. Если решение студента падает на `fatalError`, падает только этот тест. Без `--parallel` падает весь прогон, и отчёта нет вовсе.

## 12. Что не трогать

- `*.go`, `build.sh` — сам чекер;
- `payload/swift/toolchain.json` — кроме поля `minTests`;
- `payload/swift/pinned/Package.swift` — меняется только вместе с `templates/swift-homework/Package.swift`, иначе сборка остановится;
- `payload/gradle/` — Kotlin-курс, собирается так же командой `./build.sh gradle`.

## 13. Ограничения

Чекер помогает держать проверку честной, но **это не защита от целенаправленного взлома**. `Package.swift` — это Swift-код, который SwiftPM выполняет при сборке, и на Linux без песочницы. Настойчивый студент может обойти проверку, а токен компании можно достать из бинаря (раздел 8). От случайных и ленивых обходов чекер защищает: правка локальных тестов, исключение тестов из сборки и старые отчёты не пройдут.
