# Как собрать чекер для Swift-ДЗ

Чекер проверяет домашку в GitHub Actions и после успешного прогона
отправляет зачёт в Metaclass. Скрипт один раз собирает XCTest под Linux
и вшивает **готовый исполняемый файл XCTest** в Go-бинарник. В CI
заново компилируется только решение студента из `Sources/Orders`.

## Одна команда для автора тестов

На компьютере нужны Go 1.21+ и запущенный Docker. Если у вас Mac с Apple
Silicon, Docker должен уметь запускать контейнеры `linux/amd64`.
Получите у владельца курса `LMS_COMPANY_TOKEN` и `CALLBACK_TASK_ID`.
Задайте их в окружении: токен компании и ID задания вшиваются при сборке.

Из вашего Swift-проекта запустите:

```bash
/путь/к/чекеру/build.sh swift ./Tests/OrdersTests
```

Готовый файл: **`dist/checker-swift-linux-amd64`** в папке чекера.
Передавайте папку самого тестового таргета с файлами `*.swift`, а не
корень Swift-пакета. Скрипт не меняет эту папку. Если удобнее перенести
файлы в чекер, замените примеры в
[`payload/swift/tests/OrdersTests/`](../payload/swift/tests/OrdersTests/)
и запустите из корня чекера `./build.sh swift`.

Чтобы сразу установить бинарник в репозиторий, созданный из
[шаблона задания](../templates/swift-homework/), добавьте
`INSTALL_TO="/путь/к/репозиторию-задания"` перед командой. Скрипт положит
файл в `<репозиторий-задания>/.github/checker`. В шаблоне уже есть workflow
и отдельные локальные тесты. Переносить эталонные тесты к студентам не нужно.

## Какие тесты подходят

- Пишите обычные `XCTestCase` с `import XCTest` и `import Orders`.
  Обращайтесь к [публичному API шаблона](../templates/swift-homework/Sources/Orders/).
  Предсобранный раннер и решение студента связываются через этот интерфейс,
  поэтому `@testable import Orders` и доступ к `internal` здесь не подходят.
- Тесты и решение должны собираться на Linux: без UIKit, SwiftUI,
  SwiftPM-зависимостей и тестовых ресурсов. Swift Testing (`@Test`,
  `#expect`) не запускается. Пропущенный XCTest блокирует зачёт.
- Сохраните публичные сигнатуры задания. Студент может менять тела,
  приватные поля и вспомогательный код. Если меняете публичный интерфейс
  для нового выпуска, обновите шаблон и пересоберите чекер.
- Сборщик печатает `Собрано эталонных XCTest: N` и запоминает это число
  в бинарнике. Сверьте его с вашим набором; менять настройки не нужно.

## Проверка перед выдачей

Для пробной сборки можно задать
`LMS_COMPANY_TOKEN=local-check CALLBACK_TASK_ID=local-check`.
В копии репозитория задания с эталонным решением установите бинарник
в `.github/checker`, запишите `user_token: local-check` в `config.yml`
и из корня этой копии запустите:

```bash
docker run --rm --platform linux/amd64 \
  -v "$PWD:/submission:ro" -w /submission swift:6.1.3-noble \
  .github/checker --dry-run
```

Ожидаемый результат: `[checker] тестов: N, прошло: N`, код выхода 0.
Повторите проверку на заведомо неверном решении: код выхода должен быть
ненулевым. `--dry-run` не обращается к Metaclass. Для выпуска соберите
бинарник заново с выданными курсом значениями и проверьте workflow в Actions.

## Что происходит в CI

GitHub Actions запускает `.github/checker` в том же образе
`swift:6.1.3-noble`, в котором собран XCTest. Чекер компилирует
`Sources/Orders` в `libOrders.so` и запускает вшитый раннер с этой
библиотекой. Он не читает студенческий `Tests/` и не выполняет
`Package.swift`. Оба нужны только для локальной работы студента.

После завершения всего набора без ошибок и пропусков чекер читает результат
и вызывает `POST /api/v2.chunk.check_callback_task` с ID задания и
`user_token` из `config.yml`. Ответ HTTP 200 означает, что портал принял
зачёт.

Токен компании можно извлечь из выданного бинарника. Эта схема исключает
подмену эталонного набора через локальный `Tests/`, но не защищает зачёт
от намеренной подмены workflow, подделки результата из кода решения или
прямого вызова LMS владельцем репозитория. Не размещайте личный
`user_token` в публичном репозитории.
