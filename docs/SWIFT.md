# Чекер для Swift-заданий

Инструкция для автора задания. Вам нужно сделать три вещи:

1. написать задание как обычный Swift-пакет: исходники и тесты;
2. запустить одну команду:
   ```bash
   ./build.sh --tests ~/MyHomework --task-id 123 --install-to ~/MyHomework-student
   ```
3. закоммитить и запушить репозиторий для студентов.

Чекер не привязан к конкретному заданию: модули, таргеты и тесты могут называться как угодно. Код чекера (Go) трогать не нужно.

## 0. Что установить

| Что | Зачем | Как |
|---|---|---|
| Xcode 16+ (Swift 6) | писать и прогонять задание | App Store |
| Go 1.21+ | собирать бинарь чекера | `brew install go` |
| Docker (желательно) | проверить задание под Linux, где работает CI | Docker Desktop или OrbStack |

Проверка: `swift --version` и `go version` должны что-то вывести.

Сам чекер:

```bash
git clone -b ios-checker https://github.com/WhiskeyMoonlight/OrderSystemHW.git course-checker
cd course-checker
```

## 1. Задание: обычный Swift-пакет

```
MyHomework/
├── Package.swift
├── Sources/MyHomework/     исходники: заглушки, которые реализует студент
└── Tests/MyHomeworkTests/  ваши эталонные тесты
```

Имена любые. Готовый пример — [`examples/swift-orders`](../examples/swift-orders).

**Правила для тестов.** CI работает на Linux, и если их нарушить, у всех студентов пайплайн упадёт с «проект не скомпилировался»:

- **Только XCTest:** класс наследуется от `XCTestCase`, тест — `func testЧтоТо()` без параметров (можно `throws` и `async`). Тесты на swift-testing (`@Test`, `#expect`) сейчас не попадают в отчёт.
- **В тестах `@testable import MyHomework`.** Тогда студенческий код может оставаться `internal`.
- **Только стандартная библиотека и базовый Foundation.** Нельзя `UIKit`, `SwiftUI`, `Combine`, `CoreData`, `OSLog`, `XCTMetric`/`measure`, UI-тесты: на Linux их нет.
- **Деньги — целым числом** (копейки в `Int`), не `Decimal`: на Linux он ведёт себя иначе.
- **Никаких проверок, зависящих от локали машины** (`DateFormatter`, `Locale`).
- **Без зависимостей в `Package.swift`.**
- **`swift-tools-version: 5.10`** в `Package.swift`. С `6.0` включается строгий режим Swift 6, и обычный код студента может не скомпилироваться.
- **Не называйте функции задания так же, как методы `XCTestCase`** (`add`, `measure`, `expectation`, `wait`…). Иначе вызов `add(2, 3)` в тесте не скомпилируется: компилятор найдёт метод класса, а не вашу функцию.
- **Тесты независимы друг от друга:** они выполняются параллельно.

**Проверьте тесты на эталонном решении.** Временно реализуйте заглушки и запустите:

```bash
cd ~/MyHomework
swift test --parallel
```

Всё должно быть зелёным. Потом верните заглушки: студент получит их, а не решение.

## 2. Ключи LMS

Нужны два значения из LMS (Metaclass). Генерировать ничего не нужно, их выдают:

| Значение | Что это | Где взять |
|---|---|---|
| токен компании (`--lms-token`) | им чекер подписывает запрос в LMS | у владельца курса; один на все задания |
| ID задания (`--task-id`) | какое задание засчитать | в LMS; **у каждого задания свой**, поэтому и бинарь на каждое задание собирается свой |

Передать их можно тремя способами. Если одно и то же значение задано в нескольких местах, побеждает то, что выше по списку:

1. **Аргументы:** `./build.sh --lms-token XXX --task-id 123 ...`
2. **Переменные окружения:** `LMS_COMPANY_TOKEN`, `CALLBACK_TASK_ID`
3. **Файл `lms.yml`** в корне чекера (подхватывается автоматически) или любой файл через `--config путь`:
   ```bash
   cp lms.example.yml lms.yml
   ```
   ```yaml
   lms_token: ваш-токен-компании
   task_id: 123
   ```

**Удобнее всего так:** токен один раз записать в `lms.yml`, а ID задания передавать при сборке через `--task-id`. Файл `lms.yml` есть в `.gitignore` и в git не попадёт.

Третье значение — **личный токен студента**. Его вписывает сам студент в `config.yml` своего репозитория (`user_token: ...`). При сборке он не нужен.

## 3. Сборка

```bash
./build.sh --tests ~/MyHomework --task-id 123
```

В `--tests` можно передать любой из трёх вариантов:

| Что передали | Что произойдёт |
|---|---|
| папку пакета `~/MyHomework` | возьмутся `Tests/` и `Package.swift` — **рекомендуется** |
| папку `~/MyHomework/Tests` | то же самое, `Package.swift` ищется уровнем выше |
| папку таргета `~/MyHomework/Tests/MyHomeworkTests` | тесты лягут в `Tests/MyHomeworkTests` |

Что делает скрипт:

1. Проверяет ключи.
2. Упаковывает тесты. Всё содержимое папки `Tests/` копируется как есть, так что ресурсы для тестов тоже подойдут.
3. Закрепляет `Package.swift`: при проверке он заменит студенческий, и студент не сможет исключить тесты из сборки.
4. **Считает тесты** (`func test…()`) и записывает их число как минимальное. Если при проверке запустится меньше, задание не будет засчитано. Если счётчик ошибся, укажите число вручную: `--min-tests N`.
5. Собирает бинари под Linux и macOS и проверяет, что они рабочие.

В конце скрипт печатает итог: сколько тестов найдено, какой `Package.swift` закреплён и где лежат бинари:

```
dist/checker-swift-linux-amd64    ← для GitHub Actions
dist/checker-swift-darwin-arm64   ← для проверки на Mac
```

Все параметры: `./build.sh --help`.

## 4. Репозиторий для студентов

Репозиторий студента — тот же пакет, но:
- `Package.swift` **тот же самый** (при проверке он всё равно будет заменён закреплённым);
- в `Sources/` заглушки, а не ваше решение;
- `Tests/` можно оставить пустой или положить туда копию тестов, чтобы студент мог гонять их локально. При проверке папка всё равно заменится эталонной.

Установить чекер в репозиторий:

```bash
./build.sh --tests ~/MyHomework --task-id 123 --install-to ~/MyHomework-student
```

Скрипт положит бинарь в `.github/checker`. Если в репозитории их ещё нет, он также создаст:
- `.github/workflows/check.yml` — запуск проверки на каждый push (Linux, Swift 6.1);
- `config.yml` — сюда студент впишет свой токен;
- `.gitignore`.

Существующие файлы скрипт не трогает. Если ваш `Package.swift` и студенческий различаются, он предупредит. Дальше остаётся закоммитить и запушить:

```bash
cd ~/MyHomework-student
git add .
git commit -m "Задание и чекер"
git push
```

Если вы поменяли тесты, ключи или `Package.swift`, повторите команду сборки и закоммитьте новый `.github/checker`.

## 5. Проверка перед выдачей студентам

Сделайте копию студенческого репозитория, положите туда своё эталонное решение и прогоните чекер так же, как это сделает CI, но без отправки в LMS. Команды запускаются из папки чекера:

```bash
rm -rf /tmp/hw-check && cp -R ~/MyHomework-student /tmp/hw-check
cp -R <папка с вашим решением>/. /tmp/hw-check/Sources/
cp dist/checker-swift-darwin-arm64 /tmp/hw-check/checker-local
cp dist/checker-swift-linux-arm64  /tmp/hw-check/checker-linux
sed -i '' 's/PASTE_YOUR_TOKEN_HERE/test/' /tmp/hw-check/config.yml

(cd /tmp/hw-check && ./checker-local --dry-run)
```

Ожидаемый результат: `[checker] тестов: N, прошло: N, упало: 0, пропущено: 0`. Если запустить без решения, на заглушках, должно выйти `упало: N` — это тоже правильно.

**Под Linux** (так работает CI; это единственный способ заранее поймать API, которого нет на Linux):

```bash
docker run --rm -v /tmp/hw-check:/w -w /w swift:6.1 ./checker-linux --dry-run
```

`linux-arm64` — для Mac на Apple Silicon. На Mac с Intel возьмите `linux-amd64`.

Какие тесты и ключи вшиты в бинарь, можно посмотреть так: `./checker-local -print-manifest`.

## 6. Как идёт проверка в CI

При каждом push студента:

1. Чекер читает `user_token` из `config.yml`.
2. Заменяет `Tests/` на ваши тесты, а `Package.swift` на закреплённый.
3. Запускает `swift test --parallel`. Каждый тест выполняется в отдельном процессе, поэтому `fatalError` в коде студента роняет только этот тест, а не весь прогон.
4. Если все тесты прошли и их не меньше минимума, отправляет в LMS:
   ```
   POST https://lms.metaclass.kts.studio/api/v2.chunk.check_callback_task
   Authorization: Bearer <токен компании>
   {"created": "...", "task_id": "<ID задания>", "user_token": "<токен студента>",
    "extra": {"student_repo": "owner/repo", "student_ref": "refs/heads/main"}}
   ```
   При ответе 5xx или сетевой ошибке чекер делает ещё две попытки. Ответ 4xx — окончательный отказ.

## 7. Сообщения и что с ними делать

| Сообщение | Причина | Что делать |
|---|---|---|
| `не задан --lms-token` / `--task-id` | ключ не передан | раздел 2 |
| `в lms.yml осталась заглушка` | `lms.yml` скопирован, но не заполнен | впишите значения |
| `в тестах не найдено ни одного теста` | нет `func testЧтоТо()` в `XCTestCase` | раздел 1; или `--min-tests N` |
| `Package.swift рядом с тестами не найден` | передана папка не внутри пакета | передайте `--tests <папка пакета>` |
| `в config.yml не заполнен user_token` | студент не вписал токен | студенту: вписать токен из личного кабинета |
| `отчётов о тестах нет — скорее всего проект не скомпилировался` | не собрался код студента **или ваши тесты** | если так у всех — тесты используют API не для Linux или не совпадают с заглушками (разделы 1 и 5) |
| `тестов: N, прошло: M, упало: K` | обычный красный прогон | студенту: чинить решение |
| `прогнано тестов: N, ожидалось не меньше M` | часть тестов не запустилась | нет ли `@Test`? верно ли посчитано (`--min-tests`)? |
| `LMS отклонила результат: статус 401/403` | неверный токен компании | пересобрать с правильным |
| `LMS отклонила результат: статус 400/404` | неверный ID задания или токен студента | проверить `--task-id`; студенту — токен |
| `не удалось отправить результат за 3 попытки` | LMS недоступна | перезапустить job позже |

## 8. Ограничения и безопасность

- **Токен компании лежит в бинаре открытым текстом.** Тесты сжаты, простым `grep` их не найти, а токен виден через `strings .github/checker`. Бинарь коммитится в репозиторий студента, так что `LMS_COMPANY_TOKEN` фактически доступен любому студенту, который будет его искать. Так устроен и Kotlin-чекер. Что из этого следует:
  - не храните токен в git и не пересылайте его в чатах;
  - если LMS позволяет выпустить токен только на callback, используйте его;
  - если токен утёк, попросите владельца курса его перевыпустить и пересоберите бинари всех заданий.
- **Это защита от случайных и ленивых обходов, а не от целенаправленного взлома.** Подмена тестов, исключение тестов из сборки и старые отчёты не пройдут. Но `Package.swift` — это Swift-код, который выполняется при сборке, и настойчивый студент может обойти проверку.
